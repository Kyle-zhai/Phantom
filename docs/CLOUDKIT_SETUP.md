# CloudKit + Sign in with Apple — one-time setup

Phantom has no server. Two Apple services replace one:

| Need | Service | Where the data lives |
|---|---|---|
| A user's subscriptions, ratings, cancel proof, dispute letters, ledger, preferences on every device | SwiftData ↔ CloudKit **private** database (`.automatic`) | The user's own iCloud. Phantom cannot read it. |
| The Picks leaderboard (submissions, open counts, reports) | CloudKit **public** database | Apple-hosted, readable by everyone, moderated by you |
| "Who is this?" for Picks ownership + dispute-letter signature | Sign in with Apple | User id in iCloud Keychain; name/email on device |

Container: `iCloud.com.yinanzhai.phantom` (`AppConfig.cloudKitContainerID`).

## 1. Apple Developer portal (App ID `com.yinanzhai.phantom`)

**Scripted:** `./launch/register-capabilities.sh` lets Xcode automatic signing add the capabilities below to the App ID and refresh the team profile. It needs Xcode to be signed in (Xcode → Settings → Accounts) *or* the App Store Connect API key variables from `~/.zshrc` (`ASC_KEY_ID` / `ASC_ISSUER_ID` / `ASC_KEY_PATH`, Admin role). The script prints ✅ once the signed build carries the CloudKit entitlement.

Manual equivalent — enable these capabilities, then let Xcode automatic signing regenerate the profile:

- **iCloud** → CloudKit, container `iCloud.com.yinanzhai.phantom`
- **Sign in with Apple**
- **Push Notifications** (silent pushes wake the app when another device changed data; needed for `aps-environment` in the entitlements)
- **App Groups** `group.com.yinanzhai.phantom` (already required for the widget)

The entitlements file is generated by `xcodegen` from `project.yml`; unsigned simulator builds ignore them (the store then runs local-only, see `CloudSyncState`).

**Status 2026-09-10:** done — `register-capabilities.sh` ran against the signed-in Xcode account; the regenerated team profile lists the iCloud container, Sign in with Apple, Push and the App Group, and a signed device build carries all of them. Right after registration CloudKit answered `unknown container: 'iCloud.com.yinanzhai.phantom'` (code 1014) for a while — a freshly registered container takes time to propagate; opening it once in the CloudKit Console (https://icloud.developer.apple.com) also forces creation of its Development/Production environments.

**Environments:** Debug builds carry `com.apple.developer.icloud-container-environment = Development` (from `project.yml`); the Release configuration signs with `Phantom/Phantom.release.entitlements` (`Production`), so the App Store archive talks to the deployed production schema.

## 2. Private database (user data) — nothing to configure

SwiftData creates the private schema on first run in the **Development** environment. Before the App Store build: CloudKit Console → Schema → **Deploy Schema Changes to Production**. Do this again whenever a `@Model` gains a field.

Rules baked into `Models/Persistent.swift`: no `@Attribute(.unique)`, every property has a default, duplicates are collapsed on load (`Dedupe`).

## 3. Public database (Picks) — record types, indexes, security roles

**Scripted:** the whole public schema (record types, queryable indexes, security roles) is in `docs/cloudkit/phantom-public.ckdb`. Import it with `./docs/cloudkit/import-schema.sh` (development) and again with `production` once tested. The only manual prerequisite is a CloudKit **management token**, which needs your Apple ID: CloudKit Console → account menu → Manage Tokens → Generate Management Token, then `xcrun cktool save-token --type management`. Claude can't do that step.

Manual equivalent — create in CloudKit Console → Development → Schema → Record Types (the app also creates them just-in-time on first save, but the indexes and roles are manual):

**AppPick**
| Field | Type | Index |
|---|---|---|
| name, tagline, details, url, appStoreURL | String | — |
| category | String | Queryable |
| status | String | **Queryable** (list query is `status == "approved"`) |
| submitterToken | String | **Queryable** ("Your submissions") |
| reports | Int64 | — |
| screenshot | Asset | — |

**PickCounter** — `clicks` Int64, `pick` Reference(AppPick, deleteSelf). Record name is `counter-<AppPick record name>`.

**PickClick** — `pick` Reference(AppPick, deleteSelf), `day` String. Record name is `<pick>|<userToken>|<yyyymmdd>`; the name IS the one-open-per-person-per-day constraint (a second save fails with `serverRecordChanged`).

**PickReport** — `pick` Reference, `reason` String, `reporterToken` String.

**Security Roles** (Schema → Security Roles):
| Record type | `_world` | `_icloud` | `_creator` |
|---|---|---|---|
| AppPick | Read | Create | Read/Write |
| PickCounter | Read | **Create + Write** | Read/Write |
| PickClick | — | Create | Read |
| PickReport | — | Create | Read |

Only counters are world-writable, so nobody can edit another user's submission text or URL. Then **Deploy to Production**.

## 4. Picks is parked — the public database is not used

> **Parked 2026-09-11.** Picks was built but never released. Tab 3 holds the For-you
> recommendations instead, and the whole feature is now behind `#if DEBUG`, so the
> Release binary contains no CloudKit *public* database code (verified: `AppPick`,
> `PicksService` and `publicCloudDatabase` are all absent from the Release build).
>
> **Nothing in section 3 of this document is required to ship.** The public schema in
> `phantom-public.ckdb` and `import-schema.sh` are kept for a possible revival. If Picks
> is revived, restore `PicksService.shared.deleteMySubmissions()` in
> `AppStore.deleteAccount` — App Review guideline 5.1.1(v) requires account deletion to
> remove published content — and re-do the privacy answers below.

Moderation, if it ever ships: submissions save with `status = "pending"` and are
invisible until CloudKit Console → Data → Production → AppPick sets `status` to
`approved`. Reports land in **PickReport**; a reported pick hides locally for the
reporter immediately, and users can hide every pick from one submitter.

## 5. What still needs your hand before release

1. Portal capabilities above (Phantom will not archive without them). **Done** —
   `launch/register-capabilities.sh` succeeded once Xcode was signed in.
2. **Deploy the private schema to Production.** Run a *signed* build on a device or
   simulator with an iCloud account first: SwiftData creates the record types in the
   Development environment automatically. Then CloudKit Console → Schema → **Deploy
   Schema Changes** → Development to Production. Skip this and iCloud sync silently does
   nothing in the App Store build — users lose their data when they change phones. The
   public schema is *not* needed (see section 4).
3. **App Store privacy nutrition labels.** The answer sheet in
   `launch/store/APP_STORE_LISTING.md` is authoritative and `launch/store/REVIEW_CHECKLIST.md`
   must match it; the short version:
   - **Data Not Collected** across every category. The Sign in with Apple identifier is
     written to the Keychain by `AccountService` and transmitted nowhere; the only network
     requests in the app are plain GETs of the static catalogs on GitHub Pages.
   - Private-database sync is the user's own iCloud, not a Phantom data collection.
   - Listing copy: "nothing leaves your iPhone" became "your data stays on your iPhone
     and in your own iCloud — never on a Phantom server."
4. `launch/legal/PRIVACY_POLICY.md` and `docs/privacy.html` are already updated and
   published; keep the two in step if either changes. Same for
   `launch/legal/TERMS_OF_SERVICE.md` and `docs/terms.html`.
